# Controlled deployment reference

Local implementation: `python -m deployment.deploy --env dev` validates configuration, resource presence and exact local/Databricks DAG correspondence, then emits `VALIDATED_REFERENCE_PLAN` and `remote_deployed=false`. PROD plans require a SemVer release tag, for example `--env prod --release-tag v1.0.0`. This is a reviewable plan, not a remote deployment command disguised as success.

The bundle contains four paused reference jobs: daily data, daily scoring, weekly model review/training and data-quality monitoring. Task dependencies use all-success behavior. Daily data/scoring have separate entry points; do not run two competing writers over one production release. Weekly review does not retrain by default: a new-label/performance/drift review and an explicit approved retraining request precede candidate training. Candidate validation never automatically promotes to Production.

Before real deployment, implement and test the governed Delta task adapter replacing the fail-closed reference entry, supply `workspace_host`, actual approved compute, deployed entry path, catalog/schema/Volume policy and run identity. Configure the production bundle with an approved service principal, controlled deployment root ACLs and permissions. Do not use a generally writable shared production root. Then use `databricks bundle validate -t <target>` in the authenticated environment and review the plan before `databricks bundle deploy`. These workspace-dependent commands were not executed here.

CI workflows run lint/format, all tests including fixture E2E, contract/quality/ML checks, package build, repository policy, Bandit and dependency auditing. The dev/prod deployment workflows validate release plans and upload no customer data. The production job is manual, requires main, verifies the release tag points at the checked-out commit, reruns release tests and references the `production` GitHub Environment. Required reviewers/branch protection must be configured outside Git; naming the environment alone does not enforce approval. Require all CI/test/quality checks before merging/releasing. [GitHub environment protection documentation](https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments).

Use simple `main` plus short-lived `codex/*`, `feature/*` or `fix/*` branches according to team convention, PR review, passing checks and version tags. No branches are merged or remote workflows enabled by this task. Version 1.0.0 is a local project release definition; no Git tag or release was pushed.

Rollback code to a reviewed previous release; select a previous validated immutable data batch/Delta version; restore a compatible approved model version; and restore report/semantic-model release together. Never overwrite audit history or erase the failed release. Local recovery uses verified checkpoints; cloud recovery must preserve source/event lineage and Delta transaction/publication boundaries.
