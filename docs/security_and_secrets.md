# Security and secrets strategy

No credentials are introduced. `.env.example` contains only optional paths and identifiers; real `.env` files, data, local SQLite/MLflow stores, model artifacts and Power BI caches are ignored. Never put access tokens, passwords, client secrets or credential-bearing connection strings in Git, logs, notebooks, Docker layers or exported manifests.

Local developer authentication should use an approved interactive identity or workload credential provider. In Azure, prefer managed identities/workload identity federation for storage and services. Keep genuinely necessary secrets in Azure Key Vault. Databricks jobs can retrieve approved secrets from a governed secret scope (including Key Vault-backed integration where supported), and must never print the returned values. Grant the job identity only its required scope/storage/catalog rights. This repository describes retrieval; it does not configure a real vault/scope or fake an identity.

GitHub release workflows use read-only repository permissions and pinned action commits. Environment reviewers, branch protection, release-tag restrictions and OIDC trust must be configured in the repository/cloud account by their owners. No privileged `pull_request_target` workflow executes untrusted changes. Artifact uploads include aggregate test evidence/reference plans, never customer exports or runtime credentials. Review runner logs and artifact retention. Dependency updates should regenerate the hash lock, run tests and repeat vulnerability scanning.

The repository policy checks source YAML, large files, restricted runtime artifacts and selected credential patterns without echoing matched values. It is a heuristic, not proof that secrets cannot exist. Bandit checks the new operational boundary; controlled joblib model loading in the existing ML layer still requires trusted artifacts and checksum/ownership controls. Do not load downloaded model files. The full repository review records legacy scan findings separately rather than hiding or suppressing them indiscriminately.

Customer keys are pseudonymous, not anonymous. Customer-level data and explanations need authorized roles, export restrictions and retention policy. The production target should restrict network paths, storage access, catalog ownership and service identities. Hiding Power BI columns is not RLS or access control. Security behavior and approval remain external operational requirements, not claims of compliance.
