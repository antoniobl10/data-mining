# Versioned contracts and schema evolution

Seven YAML contracts cover accepted customers, products, payroll, campaigns, digital interactions, services and satisfaction. Each declares owner, technical owner, description, layer, contract version, primary key, required fields, logical types, nullability, accepted values and useful ranges. Full validation rejects null/duplicate keys, incompatible types, invalid categorical values, non-finite numeric values and range violations. Dates must already be typed datetimes; transport parsing is an explicit upstream step rather than permissive contract coercion.

The customer source is deliberately raw and may contain malformed rows. Stage 01 enforces the required source structure; the existing Silver transformer quarantines invalid content. Stage 04 applies the full accepted-customer contract and exact physical-row reconciliation. Raw diagnostic failures are not relabeled as valid Gold records. A configurable quarantine-fraction gate additionally blocks excessive rejection. DEV allows the established snapshot's approximately 28% quarantine; PROD's proposed 5% policy would reject that input. These are environment publication policies, not relaxed Silver validation rules.

Synthetic domain generation is nested in Customer 360: raw synthetic Bronze → existing domain validation/quarantine → typed Silver → full domain contracts → synthetic Gold reconciliation. Generated domain violations fail the workflow rather than silently removing rows. `contract_version` is recorded in source/contract manifests; it is a dataset envelope property, not a repeated feature column.

`src/contracts/validate.py` classifies removed/renamed fields, type changes, narrowed nullability/ranges/accepted values, new required fields and changed keys as breaking. Adding a genuinely optional field is non-breaking when extra columns are permitted. Versions are checked explicitly. Version 1.1 can add optional compatible fields; a breaking change requires 2.0, migration tests, downstream feature/BI review and a controlled coexistence or cutover plan. A renamed customer key is never guessed from similar text.

Schema compatibility does not prove semantic compatibility: units, cutoff meaning, timezone, consent and label definitions need human review. Contract changes belong in the PR template and the changelog. An incompatible source should remain in Bronze/quarantine with an alert and should never advance the BI release pointer.
