# Quality, audit and observability

The local operational store is `data/platform/<env>/monitoring/platform.sqlite`. It exposes `pipeline_audit`, `quality_checks`, `pipeline_observability` and an alert outbox. Equivalent Gold/monitoring schema names in the production target should be governed Delta technical datasets, not business facts. Parquet mirrors support offline inspection; Power BI CSV snapshots are included in successful exports.

Audit rows identify pipeline/run, environment, task, batch, attempt, start/end/duration, state, read/written counts, warning/error counts, redacted errors, code version, source version and output location. States are PENDING/RUNNING/SUCCESS/WARNING/FAILED/SKIPPED in checkpoints; audit rows record executed attempts. Failed attempt history remains after a successful resume. Reused successful checkpoints do not create duplicate processing/audit rows. A task left RUNNING by process death receives a new attempt on resume. Counts across stages are throughput counts, not unique customers.

Standard quality rows contain `check_id`, dataset, layer, dimension, name, expected/actual, status, severity, timestamp and pipeline run ID. Dimensions include completeness, uniqueness, validity, consistency, referential integrity, freshness, volume and distribution diagnostics. CRITICAL failures stop progression; WARNING results remain visible and continue; INFO establishes a baseline or diagnostic. Existing 69 Gold and 62 synthetic Gold checks are reused, alongside row coverage, probability range, contact exclusions and export reconciliation. Seven contracts are additional full-schema gates.

Freshness uses the real UTC clock, not the generator cutoff or the file's new ingestion time. Design thresholds are 24 hours for the source, six hours for campaigns, two hours for digital events. The frozen historical demo is genuinely stale and produces DEV/TEST warnings. PROD would treat freshness failures as critical. Late/future timestamps also require investigation. New ingestion does not make old customer behavior current.

Volume compares the current published customer population with the previous successful release; no baseline yields INFO. A 20% relative change warns; an 80% change is critical. Row-level reconciliation also catches lost/duplicated data. On later releases, selected feature/score distributions are compared with the previous release using the existing PSI/KS descriptive diagnostics. Those diagnostics do not prove concept drift, which needs matured future labels. The initial monitoring sample is not a rolling-average implementation; sustained seasonality needs additional historical baselines.

Structured JSON logs include timestamp, level, pipeline run, batch, environment, component/task and message. The orchestration adapter propagates context into existing Bronze/Silver logger events. No customer records or credentials are logged. The redactor is defense in depth; services should avoid constructing secret-containing error text. External delivery remains disabled: alerts are local payloads with environment, pipeline, task, run, timestamp, severity, redacted error and log reference. Configure approved Azure Monitor/webhook delivery separately, including deduplication, resolution and on-call policy.

Duration and row throughput come from real audit attempts. Health reporting distinguishes final pipeline status from failed retries, warning freshness and quality gates. Memory and cloud cost are not benchmarked for this small demo. No achieved production uptime/SLA is asserted.
